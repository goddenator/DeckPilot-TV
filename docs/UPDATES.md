## On the Steam Deck

Open **DeckPilot → Settings → Updates**. Stable is the default. **Enable Preview → Confirm** opts into approved development prereleases; choosing either channel only checks/downloads, never installs or silently downgrades.

1. **Check for Updates** verifies and caches both components from the same release. You see the app/plugin versions and exact build commit. The background app checks every six hours; the plugin can check even when the old app cannot understand channels.
2. **Update App → Confirm** starts the existing SteamOS user service updater, saves the previous application, replaces only its three runtime files, restarts and checks its full build ID. Failed restart restores the previous files. An interrupted operation retains a persistent recovery snapshot and exposes **Recover Interrupted Update**. Game settings, saves, game backups, preferences and Drive configuration are never part of the replacement.
3. After the matching app is healthy, **Install Plugin in Decky → Confirm** snapshots the current plugin into user data, verifies the staged ZIP again, and copies a five-minute local installation link. DeckPilot opens Decky's Developer settings. Enable Decky's Developer mode once if necessary, paste into **Install from URL**, and accept Decky's warnings/installation confirmation. The exact label/route and clipboard behavior need hardware testing. If copying fails, a selectable link remains visible.

The plugin does **not** have a supported public installer API. The implementation uses Decky Loader's documented Install from URL feature, not private `DeckyBackend` methods, root writes, auth scraping or replacing plugin directories. Extra Decky paste/confirmation taps are required. It serves already verified bytes only on 127.0.0.1, under an unpredictable URL, for five minutes; there is no directory browser. Decky remains responsible for unloading, installation and reload. A prepared link is never reported as an installed plugin. Nothing touches other plugins.

**Restore Previous App** and **Restore Previous Plugin** are separate confirmed actions. Plugin rollback uses the same Decky installation confirmation. If Loader fails or the new plugin will not load, open the DeckPilot Desktop dashboard and choose **Prepare Plugin Rollback**, then paste that local link into Decky’s Developer settings. This recovery path uses the running app and does not depend on the plugin frontend. A trusted previous published plugin URL is the fallback if neither new interface starts. Unlike app recovery, Loader installation is not an atomic two-component transaction. App-first order and a version-mismatch warning prevent new profile/Play controls until both components match. The ordinary Steam Play button remains available. A same-version app repair is not offered automatically.

Normal pushes/PRs run tests and upload build artifacts only. Tags no longer publish releases. The owner subsequently ran the protected preflight successfully and approved a publication attempt for `v0.8.3-preview.1`. That attempt left draft release `440744496` unpublished after its post-upload tag lookup failed. This correction has not modified that draft, applied publication labels, or created any tag, release or merge.

Before publication, configure GitHub Environments **deckpilot-preview-publish** and **deckpilot-stable-publish** with **goddenator as the sole required reviewer**, and restrict who can edit those environments/workflows. GitHub accepts any one listed environment reviewer, so listing additional reviewers would weaken the owner-only requirement and is rejected. For an owner-triggered run, leave Prevent self-review disabled so the owner can explicitly approve their own build; disable administrator bypass if the approval must never be skipped. This is available for this public repository without paid services. The workflow refuses publication if the required owner reviewer is absent; a newly auto-created unprotected environment is insufficient.

The guard requests `contents: read` for checkout and `actions: read` for the environment API. The protected publisher explicitly requests `contents: write`, `pull-requests: read` and `actions: read`; job permissions replace rather than extend top-level permissions. The last two read scopes cover the PR-head and environment-protection rechecks after approval. A same-repository `pull_request: labeled` run retains explicitly requested `contents: write`; fork PRs are rejected. Do not switch to `pull_request_target` or grant write-all/admin scopes.

For an unmerged Preview, apply the explicit **deckpilot:publish-preview** label to the reviewed PR. The `pull_request: labeled` workflow freezes that PR's full SHA, verifies the environment protection and then waits for the owner's environment approval. Remove/reapply the label after new commits; publication rechecks the PR head after approval and fails if it moved or closed. This route permits approved preview releases without merging main. The separate manual dispatch route becomes available once this workflow exists on the default branch; it accepts an exact reviewed SHA, Stable/Preview selection and Preflight/Publish mode (Preflight by default). Nothing is published on ordinary pushes or simply opening a PR.

**Non-publishing verification:** ordinary same-repository PR CI includes a read-only permission/environment preflight with the same requested token scopes as the publisher. It never checks out or executes PR code, creates a deployment or sends any write request. It reads the exact PR head and Preview environment; permission errors fail the job, while an unavailable environment or missing owner reviewer is explicitly reported as **publication BLOCKED**, not proof of readiness.

To rehearse the complete GitHub environment approval path on this unmerged branch, apply **deckpilot:preflight-preview** instead of the publication label. Both modes pass the same guard, protected environment and post-approval checks. After owner approval, Preflight builds/tests/packages the exact feature SHA, runs `publish_approved.py --preflight`, checks that the tag/release is unused, validates local CLI help and prints the proposed command plan. It never invokes draft creation, tagging, upload or release publication. It cannot fall through into the Publish-only step. No protected preflight or publication label was applied by this correction. Actual owner approval remains a manual GitHub action and is not established by mocked tests or ordinary CI.

The protected job reruns Python, typecheck, frontend build and UI tests at the approved SHA. `tools/package_release.py` emits:

- `DeckPilot_TV_v<full-version>.zip`
- `DeckPilot_Decky_v<full-version>.zip` (includes `update_client.py`)
- `DeckPilot-Update.json` (repository, exact commit, channel, versions, size/SHA256 and protocols)
- `SHA256SUMS`

`tools/publish_approved.py` refuses non-Actions invocation, unapproved modes, mismatched version/channel/commit/checksums, existing tags and release collisions. It lists **all authenticated release pages, including drafts** before creation; a missing public tag lookup is never considered proof that a draft is absent. After `gh release create --draft` uploads the four assets, it discovers the **unique exact tag match**, obtains the numeric release ID and reads `/releases/<id>`. It checks the release API repository URL, ID, draft state, prerelease/channel, exact tag, full approved commit, exact four unique asset names, upload state, sizes and **all four GitHub SHA256 digests** against the locally validated manifest and checksum file. It repeats verification immediately before the only finalization request, `PATCH /releases/<id>` with `draft=false`. It never uses `/releases/tags/<tag>` to look up or finalize a draft. Pre-publication API errors, duplicate matches or metadata changes stop before finalization. If the final PATCH has an uncertain network result, inspect the release by ID before any retry; do not assume it is still a draft, automatically retry, or unpublish it.

Preview requires `X.Y.Z-preview.N` and a GitHub prerelease; Stable requires numeric `X.Y.Z` and a normal release. Bump all source/app/plugin versions together for each new build; never overwrite a tag. ZIP timestamps/permissions and file ordering are reproducible for identical source/build output, so a same-commit retry can match the original four hashes. If build tooling/dependencies produce different bytes, recovery refuses them; do not weaken verification or overwrite assets to force a match.

### Explicit draft recovery and the failed first Preview

Recovery is **opt-in**, passes the same required-owner environment gate, and requires a **fresh approval** of the exact current feature head and recovery ID. An existing draft never causes a normal Publish run to silently switch to recovery.

- On an unmerged same-repository PR, use `deckpilot:preflight-recovery:<ID>` for a read-only protected rehearsal; use `deckpilot:recover-preview:<ID>` only after review to request finalization. No recovery label was applied by this fix. The numeric ID is captured in guard outputs and rechecked after approval and immediately before publication.
- Where workflow dispatch is available, choose Preflight or Recover and enter the exact `recovery_id`. Publish mode rejects a recovery ID. Recover mode without an ID is invalid.
- Recovery requires the existing draft to be the unique release for the exact tag and to match the **newly approved checkout commit**, channel and all four local asset hashes/sizes. An absent tag is acceptable; an existing lightweight/annotated tag must resolve to that same approved commit. A published release, missing/extra/duplicate asset, changed digest, wrong commit/channel/repository/ID, or stale PR approval blocks recovery.
- Recovery issues **no create/upload/delete/replace request**. After repeated verification its only mutation is finalizing the exact verified draft by numeric ID. Incomplete or altered drafts remain unpublished for explicit owner investigation; no automatic cleanup or rollback of release state occurs.

## Trust and recovery limits

The update source is fixed to `goddenator/DeckPilot-TV`; no arbitrary repository, Actions artifact, draft or temporary third-party package is accepted. The client requires both paired components, exact full versions, schema 2/update protocol 1, allowlisted ZIP members and identities, bounded sizes, safe HTTPS redirects, GitHub asset digests and cross-matching manifest/checksums. Cached files and the captured approval token are checked again before installation. Channel changes invalidate approval. Returning from Preview to an older Stable requires an explicit downgrade confirmation.

GitHub HTTPS and digests provide source/integrity checks, not an independent developer signature or protection from a compromised repository/publisher account. The release manifest is trusted as owner-published metadata; it is not a GitHub attestation. No API key or paid API is required for public checks; unauthenticated GitHub rate limits/network failures are shown. An already verified staged build remains usable offline after a failed check. The feed scans up to 150 recent releases. Incomplete or incompatible latest channel releases fail closed rather than silently installing an older build.
