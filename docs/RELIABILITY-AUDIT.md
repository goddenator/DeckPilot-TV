# Reliability audit — 0.8.3-preview.3

This is an implementation audit and fault-injection report, not a claim that every possible defect is eliminated. It addresses issue #6 and reviews the major runtime components. The four screens and exactly Best Graphics / Best Performance / Balanced remain. No saves, Steam launch options, unsupported game configurations, published tags or releases were changed. Preview.2 is an immutable previous build; this branch prepares a new Preview.3 requiring separate review and publication approval.

## Scope and evidence

Inspected implementation: `app/deckpilot.py` (detection, adapters, process evidence, locks, previews/apply/restore, research/cache, metrics, HTTP, diagnostic and Drive paths), `app/updater.py` (trust validation, staging, app transactions, recovery, plugin snapshots/handoff), `decky/main.py` (identity, environment, subprocess and RPC handling), `decky/src/{App,LaunchView,Updates,launch,launchController,api}` (navigation, async state, focus, launch and updates), installation scripts, packager, publisher and protected workflows. Existing tests were inspected and exercised alongside new fault cases. Public-source availability, Steam internals, controller focus and OS behavior cannot be established by mocked tests.

Issue #6's code defect is confirmed: any unreadable own-user `/proc/<pid>/environ` previously returned True for every requested game. That can reproduce the reported symptom. Which exact PID/permission condition occurred on the user's device is still unknown; no private process environment or device log was collected.

## Defects fixed

| ID | Confirmed code problem | Correction and evidence |
|---|---|---|
| F01 | Unrelated unreadable processes were labelled “already running.” | Tri-state `running/closed/uncertain`; only exact identified live app processes confirm running. Several unreadable Steam helpers no longer make every game running. Unknown visibility blocks writes without claiming running. |
| F02 | Inherited App IDs on Steam/Proton helpers and zombies were counted as a running game. | Ignore foreign UID/zombies/exited PIDs; classify matched helpers and Wine service executables as uncertain. Native and Wine game evidence tested separately. No executable-name-only game match. |
| F03 | PID races/reuse and contradictory app environment IDs were not reconciled. | Compare process start identity before/after reading; changing identity or conflicting IDs yields uncertainty. Normal scheduler state changes do not imply PID reuse. Reads, process count, result count and scan time are bounded. |
| F04 | An unknown backend status could auto-launch through the old controller's generic failure fallback. | New launch protocol 2 exposes uncertainty as advice plus native Steam fallback; old protocol clients receive a recognized blocking status. Mutations retain fresh conservative checks. New plugin requires protocol 2 to expose controlled Play. |
| F05 | A closed-game plan could become stale while its prompt remained open. | Fresh cache-free local process/profile/install check immediately before `RunGame`; uncertainty, failure or a newly running game blocks dispatch. The dispatch phase locks repeated presses before awaiting this check. |
| F06 | A successful process exit with malformed approval output was treated as success; killed/failed approval results did not identify partial-state uncertainty. | Bridge marks timeout/nonzero/malformed approval results uncertain. Controller blocks automatic launch and further controlled apply on unknown mutation results. |
| F07 | Manifest filename and embedded App ID could disagree; invalid IDs were accepted as installed. | Require canonical 32-bit Steam ID and exact `appmanifest_<id>.acf` identity. Do not infer Final Fantasy X's ID from its name. |
| F08 | A symlinked Proton prefix could resolve configuration discovery outside the intended library. | Reject symlinked prefix ancestry; retain format/path allowlists. Suspicious files become unsupported rather than writable. |
| F09 | Duplicate Unreal sections could be transformed inconsistently; preview flattened similarly named keys from unrelated sections. | Reject duplicate managed sections. Preview extracts only managed section/key pairs, case-insensitively, and retains unrelated sections. |
| F10 | A damaged original backup could be restored, reused or shown as restorable without checking its content. | New records store original backup SHA256. Restore, reapply and Checkup verify it; backup hashing is size-bounded. Fault tests corrupt the backup and prove current config is unchanged. |
| F11 | A malformed backup-state record could point restore at an unrelated file, including a save. | Restore additionally requires a currently installed game's discovered allowlisted adapter path. A forged save-path record cannot overwrite the save. Backups of uninstalled/unsupported games remain on disk but are not restored automatically. |
| F12 | An empty app recovery `files` dictionary passed validation and could delete runtime files. | Recovery requires `deckpilot.py`, an allowlisted nonempty record and valid SHA256 entries before touching any file. |
| F13 | Updates started another status request every three seconds even if the previous request had not returned. | Polling now allows one outstanding request and stops scheduling after component cleanup. |
| F14 | Ordinary screen refresh invoked `rclone listremotes`, potentially waiting 15 seconds repeatedly. | Screen refresh reads saved cloud state only. Explicit cloud status/setup/upload retains actual connection checks. A negative test rejects subprocess invocation during state refresh. |
| F15 | Diagnostics read an entire growing log before slicing its tail. | Seek/read only the final 100 KB; exported log lines remain bounded and redacted. |
| F17 | A malformed profile default (list/dict) caused an unhashable-type crash during screen refresh. | Type-check before mode membership; malformed profile state falls back to Balanced. |
| F16 | Newly created application/backup/report directories inherited potentially permissive default modes. | New private directories request 0700; atomic metadata/cloud ZIP files already use private temporary files. Existing directory permissions are not silently rewritten. |

## Decisions by operation and interoperability

Process evidence includes only requested App ID, state, source, reason code and scanned count—never raw environment, full commands, executable paths, process names or personal data. Advanced Game Checkup shows evidence; `process-status <appid>` is available for local developers, but users need no terminal. Manual diagnostic exports include at most eight fresh game checks. Automatic Drive reports omit process checks, even when general diagnostic uploads are enabled.

Closed means no target evidence or opaque unknown own-user process was found in the completed bounded scan. It is not a Steam-native guarantee. Running requires exact target environment evidence and a live non-helper executable, with Wine command identity where necessary. Uncertain includes inaccessible unknown processes, ambiguous helpers, changed identity, conflicting IDs and scan limits. An unreadable known Steam helper is ignored only when process name and executable identity both corroborate helper status; a name alone is insufficient. No supported/tested Steam running-state API was available to reconcile this with Steam's UI; none was invented or patched.

While uncertain: advice and three mode preferences remain non-mutating; no settings apply/restore or DeckPilot dispatch is permitted, including Don't Ask Again. The UI says **Cannot confirm game closed**, hides unsafe action buttons and directs the user to native Steam Play/Resume. Native Steam is never intercepted or blocked. Protocol 1 pending requests cannot turn this new status into a generic auto-launch fallback.

All mutation boundaries still probe state again. There is no cache of “closed” used to authorize writes. No Internet call is added to the pre-launch guard. App/plugin full-version compatibility checks remain, and protocol 2 prevents the older controller from interpreting new process states unsafely.

## Component review and retained safeguards

- **Detection:** Steam library VDF and manifest readers support multiple resolved library roots; tools/DLC manifests may still appear in the list. Proton paths and existing native Unity adapters are separate. Steam shortcut IDs, wrappers and non-Steam processes are not guessed. Exact IDs, not title substrings, drive lookup and launch.
- **Settings:** three presets remain conservative recommendations, not measured optimal settings. Supported Unreal-format settings and existing native Unity resolution keys only. UTF-16/oversized/unreadable files fail closed. Preview tokens bind files, content, mode and selected profile. Newer manual edits remain protected. Duplicate keys and now duplicate sections reject transformation.
- **Decky:** four-screen layout, controller-sized buttons, pagination, post-save focus handling, async busy guards, cancellation and visible errors retained. Updates polling has backpressure. No broad redesign or new default technical panel was added. Real Steam focus/keyboard semantics remain unverified by browser shims.
- **Controlled Play:** no native hook, cancel/relaunch observer or automatic retry. Per-game dismissal is persisted; launch and mutation uncertainty remain distinct. Late plan/preview callbacks and repeated presses are guarded. Pre-dispatch checks address a newly running game; native launch response uncertainty remains a manual Steam fallback.
- **Updates/publishing:** source fixed to the repository, paired versions/protocols, exact manifests, GitHub digests, bounded safe ZIPs and approval tokens retained. Stable/Preview selection never installs. Failed-download/offline-cache and interrupted-update tests run. App and plugin are separate installation transactions; Decky installs only through its supported confirmed URL flow. Draft recovery remains explicit and owner-gated, with exact commit and four digests; this audit does not touch existing releases or drafts.
- **Recovery:** original configuration backups precede changes; atomic replacements and cross-process settings/update locks remain. App transaction recovery persists across simulated process death. No automatic scan/repair of save files or unrelated paths exists.
- **Performance:** live proc work is bounded, no blind stale “closed” cache added. Research has bounded deadlines/cache retention and independently labelled sources. MangoHud analysis is read-only, bounded and cached by file metadata. Game enumeration and adapter scans still repeat across RPC subprocesses; further caching needs invalidation tests before use in safety decisions.
- **SteamOS/privilege:** bridge still drops root to deck UID/GID/groups, fixes HOME/runtime/user D-Bus and allowlists inherited variables. No shell interpolation of IDs, titles or online text. Existing root/drop-user tests continue. User service availability, proc restrictions and actual Decky reload need device tests.
- **Privacy/security:** loopback Host/Origin/token checks, bounded HTTP bodies, trusted HTTPS redirect rules, bounded source parsing and explicit Drive opt-in remain. Online reports are data, never commands. No rclone stderr/OAuth configuration is exported. Process evidence is local-only by default. Directory hardening is limited to newly created application-owned paths.

## Unresolved risks and limits (not claimed fixed)

1. **Process evidence is heuristic.** SteamOS hidepid, unrecognized native launch wrappers, protected processes and stale helper IDs can yield uncertainty. Environment variables are not cryptographic identity. A same-user executable with stale exact IDs may still look active. Physical tests must establish whether the reason codes resolve the two reports; no native Steam running API is claimed.
2. **Race remains after the final check.** There is no atomic transaction spanning `/proc`, game creation and Steam `RunGame`. A separate native Play press at the same instant can race. We do not patch Steam or claim total prevention of external duplicate launches.
3. **Multi-file settings are not an all-or-nothing transaction.** If the game starts, storage fills, permissions change or the process dies between files, some approved files may have changed. Originals are preserved and uncertainty prevents automatic launch. A crash after backup-state persistence but before config replacement can leave a conservative stale record requiring manual review. No forced compensation writes to potentially running games were added.
4. **Legacy backups lack recorded original hashes.** New backups are checked. Existing old records retain their prior restore semantics; we cannot retroactively prove original authenticity. Missing/corrupted legacy backup records require review. Automatic restore of uninstalled games is intentionally blocked; files remain preserved for manual recovery.
5. **Two-component update rollback is not atomic.** App recovery does not automatically restore Decky, and a broken plugin can require the Desktop rollback handoff. Network failure during final release PATCH can leave uncertain publication state; no automatic retry/unpublish exists. No publishing/recovery was exercised live in this audit.
6. **Disk and durability:** cache/backups/orphan recovery directories can accumulate. File fsync/atomic rename does not prove resilience to every filesystem, sudden power loss, SD-card error or directory-sync gap. Existing private directory permissions are not migrated; inherited ACLs and pre-existing symlinks merit on-device review.
7. **Security boundaries:** a compromised same-user account/repository publisher can tamper with its own files and metadata. Local HTTPS/digests are not independent signatures. Diagnostic redaction is best-effort; review an export before sharing. UTF-8 BOM-only edits are normalized by the current text fingerprint and may not be distinguished from identical decoded content.
8. **UI/performance:** actual Gaming Mode controller focus, Steam overlay resize/scroll, virtual keyboard and plugin unload/reload may differ from browser mocks. Locks are blocking and some IPC requests can wait for another operation; they are not a hard real-time system. Very large libraries still cost repeated filesystem scans. No measured Deck FPS, RAM or TV benchmark is claimed.
9. **External services/hardware:** research source changes/robots restrictions, GitHub rate limits, Drive OAuth/network interruption, real SteamOS systemd-run/user service behavior, display/VRR and game-specific graphics outcomes require hardware/live checks. Unsupported titles remain advisory; no compatibility is inferred from a game name alone.

## Controller-only Steam Deck checklist

After review and a separately approved Preview.3 release, update through DeckPilot Settings → Updates → Preview, app first then the Decky-approved plugin URL installation. No Windows ZIP transfer or terminal is needed. Confirm app/plugin both show Preview.3. Do not overwrite Preview.2 or merge main.

1. In Steam, open **American Truck Simulator (270880)**. Confirm Steam shows **Play**, not Resume/Stop. Record whether native Steam Play works, then close it through Steam and wait until Play returns.
2. Open DeckPilot Find Games → that exact App ID → Advanced → Refresh Game Checkup. Record displayed state/reason (a photo is sufficient). Do the same for Final Fantasy X **after verifying its App ID in your actual library**; do not guess the ID from the title.
3. With the game confirmed closed, enable Play recommendations and choose Play with DeckPilot. If uncertain, expect **Cannot confirm game closed**, advice and Cancel/native Steam fallback—never “Already running.” Confirm no Apply/Play Without Changes/Don't Ask action dispatches under uncertainty. Native Steam should still work.
4. If closed, try Play Without Changes once; repeated presses must not launch twice. Close the game and retry after the cooldown. While the game really runs, advice/Checkup must block edits; use native Steam to resume.
5. Cancel during advice/preview, change selected profile, and start through Steam while a DeckPilot prompt is open. DeckPilot must not apply or dispatch after it detects a running/uncertain game. Do not deliberately race writes against a running game.
6. For an actually supported existing config (not ATS/FFX merely by name), review the exact keys before approving each mode. Confirm backup/restore, preserve a newer manual edit and verify saves remain unchanged. Unsupported formats must offer advice only.
7. Test Don't Ask Again while closed, reset it in Advanced, reopen Decky, test both profiles and controller focus/scroll. Review a local diagnostic export; process evidence must contain no environment, full command or private paths, and must be absent from automatic Drive reports.
8. After preserving known-good backups, test approved update/restart/rollback, offline checks and plugin handoff. Forced power interruption, SD removal and destructive storage tests should not be attempted on irreplaceable data; the simulated faults do not constitute device validation.
